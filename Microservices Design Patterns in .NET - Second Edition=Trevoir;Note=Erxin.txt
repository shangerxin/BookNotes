# Synchronous communicaton between microservices 
- Key characteristics include the following:

Immediate response: The requesting service expects an instant reply, leading to a tightly coupled interaction
Blocking behavior: The caller is halted until the response is received, which can impact performance if the callee is slow or unresponsive
Simplified error handling: Errors can be detected and managed promptly, as the caller is immediately aware of the outcome

- using gPRC, which allows us to call a REST API with higher throughput and less latency.

- Resilience: We must ensure that our service calls are done via durable channels. Remember that hardware can fail, or there can be a network outage when the service call is executed.

- Tracing and monitoring: We have established that a single operation can span multiple services.

- The categories of status codes are the following:

1xx (Informational): Communicates protocol-level information
2xx (Success): Indicates that the request was accepted and no errors occurred during processing
3xx (Redirection): Indicates that an alternative route needs to be taken to complete the original request
4xx (Client Error): General range for errors that arise from the request, such as poorly formed data (400) or a wrong address (404)
5xx (Server Error): These errors indicate that the server failed to complete the task for some unforeseen reason

namespace AppointmentsApi.Services;

    Guid DoctorId,
    string FirstName,
    string LastName,
    string Specialty
);
public class DoctorsApiClient
{
    private readonly HttpClient _httpClient;
    public DoctorsApiClient(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }
    // Example method to retrieve doctor details
    public async Task<Doctor> GetDoctorAsync(Guid doctorId)
    {
        var response = await
            _httpClient.GetAsync($"/api/doctors/{doctorId}");
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<Doctor>();
    }
}

- grpc api communication

In the 1960s and 1970s, Remote Procedure Call (RPC) emerged, enabling a program to execute a procedure on a remote server as if it were local.

RPC implementations often led to tight coupling between the client and server

gRPC include the following:

Compactness: Produces smaller payloads, reducing network bandwidth usage
Faster serialization and deserialization: Protocol Buffers (Protobuf)’s binary format allows quicker processing than REST’s text-based JSON
Server streaming: The server can send multiple responses to a single client request, which is beneficial for delivering continuous data streams
Client streaming: The client sends requests to the server, which processes them and returns a single response
Bidirectional streaming: Both the client and server exchange messages simultaneously, enabling real-time communication

RESTful APIs to gRPC, we are introduced to HTTP/2

Multiplexing: Allows multiple requests and responses to be sent concurrently over a single TCP connection
Binary framing and compression: This method utilizes a compact binary format for data transmission

public class DocumentServiceImpl : DocumentService.DocumentServiceBase
{
    // Simulating a data store
    private static readonly List<Document> Documents = new List<Document>
    {
        new Document { Id = "1", PatientId = "123", Name = "Document1" },
        new Document { Id = "2", PatientId = "456", Name = "Document2" }
    };
    public override Task<DocumentList> GetAll(PatientId request,
        ServerCallContext context)
    {
        var documentList = new DocumentList();
        documentList.Documents.AddRange(Documents.Where(
            q => q.Id == request.Id));
        return Task.FromResult(documentList);
    }
    public override Task<Document> Get(DocumentId request,
        ServerCallContext context)
    {
        var document = Documents.Find(doc => doc.Id == request.Id);
        if (document == null)
        {
            throw new RpcException(new Status(StatusCode.NotFound,
                "Document not found"));
        }
        return Task.FromResult(document);
    }
}

- message bus 

Apache Kafka: A distributed streaming platform for high-throughput and low-latency message processing:
    Pros: Handles large volumes of data efficiently; suitable for real-time analytics and event streaming
    Cons: More complex to set up and manage; may be overkill for simple messaging needs
Azure Service Bus: A fully managed enterprise message broker with rich features:
    Pros: Seamless integration with Azure services; supports advanced messaging scenarios
    Cons: Tied to the Azure ecosystem; potential cost considerations
Amazon SQS: AWS’s fully managed message queuing service:
    Pros: Scalable and easy to use; integrates well with other AWS services
    Cons: Limited to queue-based messaging; lacks some advanced features of other brokers
NATS: A lightweight, high-performance messaging system:
    Pros: Simple design; low latency; suitable for cloud-native applications
    Cons: Limited persistence options; fewer features than more comprehensive brokers
ActiveMQ: An open source message broker that supports multiple protocols:
    Pros: Supports a wide range of protocols; flexible and mature
    Cons: Can be resource-intensive; may require more maintenance
RabbitMQ: An open source message broker that facilitates asynchronous communication between distributed systems by implementing several protocols:
    Pros: RabbitMQ supports multiple protocols and is highly interoperable
    Cons: Not as performant for higher workloads and does not support event streaming

- error handling HTTP calls can be managed with native try-catch logic. With API calls, we can expect one of three kinds of errors:

Transient errors: Temporary issues such as network timeouts or rate limiting. These can often be resolved by retrying.
Permanent errors: Issues such as 404 Not Found or 401 Unauthorized. Retrying is usually unnecessary.
Unexpected errors: Unexpected conditions, such as deserialization errors or null references.

-  event typically contains the following attributes:

Timestamp: The exact time when the event occurred
Event ID: A unique identifier for the event
Aggregate ID: An identifier that ties the event to a specific entity or process
Payload: Additional data capturing the event’s details (e.g., appointment ID, patient details, etc.)
Metadata: Optional data providing context, such as the event’s source (such as the model or data type name) or the schema’s version

# implmenting trfansactions across microservices using saga pattern 
- Traditional monolithic applications rely on Atomicity, Consistency, Isolation, and Durability (ACID) transactions

- microservices application is best implemented using the Database-Per-Service pattern. 

- spans multiple services as a saga.

Reversible: These are transactions that another transaction with the opposite effect can reverse.
Retriable: These transactions are guaranteed to succeed and are implemented after pivot transactions.
Pivot: As the name suggests, the success or failure of these transactions is pivotal to the continuation of the saga.
