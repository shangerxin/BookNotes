# Clean architecture 
- dependency rule states that dependencies must flow from more concrete and low-level concerns toward less concrete high-level concerns. In a typical onion-style circle diagram

- the single responsibility principle (SRP). This falls naturally from the application of the separation of concerns noted earlier, and by combining SRP with the dependency rule

-  main components of clean architecture are as follows:

Entities and aggregates
Use cases
Interfaces
Controllers, pages, and endpoints, Controllers, pages, and endpoints represent typical ASP.NET Core UI elements. These should be kept in the UI (Web) project, or in some cases, shared base classes or reusable components
Gateways

- project structures 

organizing the application's code base:

The Entities folder will contain all the application's domain models
The Interfaces folder will contain the interfaces used to interact with other parts of the application
The UseCases folder will contain the core business logic of the application

    + The Application layer serves as a bridge between the UI and the Domain layer. Its primary responsibilities include the following:

Defining the application's use cases and high-level business logic
Orchestrating the flow of data and interactions between the UI, Domain layer, and external services
Handling input validation, authentication, authorization, and other application-specific concerns
Implementing application-specific business rules and workflows

    + Domain layer represents the heart of your app, encapsulating the core business logic and domain-specific rules. Its primary responsibilities include the following:

Defining entities that represent the key business concepts and their behavior
Implementing domain-specific rules and invariants that govern the behavior of entities
Ensuring the integrity, consistency, and validity of domain data and business operations
Providing domain-specific operations and services required by the application

    + alternative mapping libraries include the following:

Mapster: Mapster is a lightweight and fast object-to-object mapper for .NET. It offers a simple and fluent API for configuring mappings and supports convention-based mapping as well as explicit mappings. Mapster is known for its performance and ease of use.
TinyMapper: TinyMapper is another lightweight mapper that focuses on simplicity and performance. It offers a minimalistic API and supports automatic mapping based on naming conventions. TinyMapper is designed to be easy to set up and use without any complex configuration.

public class ProcessPaymentInputValidator : AbstractValidator<ProcessPaymentInput>
{
    public ProcessPaymentInputValidator()
    {
        RuleFor(x => x.UserId).NotEmpty();
        RuleFor(x => x.Items).NotEmpty();
        RuleForEach(x => x.Items).SetValidator(new ShoppingCartItemValidator());

        RuleFor(x => x.CardNumber)
            .NotEmpty()
            .CreditCard()
            .WithMessage("Invalid card number.");

        RuleFor(x => x.CardHolderName)
            .NotEmpty();

        RuleFor(x => x.ExpirationMonthYear)
            .Matches(@"^(0[1-9]|1[0-2])\/\d{2}$")
            .WithMessage("Expiration must be in MM/YY format.");

        RuleFor(x => x.CVV)
            .Matches(@"^\d{3,4}$")
            .WithMessage("CVV must be 3 or 4 digits.");

        RuleFor(x => x.PostalCode)
            .NotEmpty();
    }
}

- MediatR folder within the Infrastructure project and add a new file named ValidationBehavior.cs.

namespace Infrastructure.MediatR;

public class ValidationBehavior<TRequest, TResponse>(IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    public async Task<TResponse> Handle(
        TRequest request,
        RequestHandlerDelegate<TResponse> next,
        CancellationToken cancellationToken)
    {
        var context = new ValidationContext<TRequest>(request);

        var failures = await Task.WhenAll(validators.Select(v => v.ValidateAsync(context, cancellationToken)));
        var errors = failures.SelectMany(f => f.Errors).Where(f => f != null).ToList();

        if (errors.Count != 0)
            throw new ValidationException(errors);

        return await next(cancellationToken);
    }
}
